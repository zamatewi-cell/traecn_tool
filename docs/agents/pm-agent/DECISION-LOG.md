### DEC-001: 多 Agent 协作架构

**日期**: 2026-03-15  
**提出者**: PM-Agent  
**状态**: ? 已实施

#### 背景

项目复杂度较高，需要多个专业领域协作。单一 Agent 难以同时处理协议逆向、API 开发、认证管理、队列调度、测试验证等多个专业领域。

#### 决策

采用多 Agent 协作架构：
- 7 个专业 Agent 分工协作
- 基于文档的异步沟通
- 明确依赖关系和交付标准
- 每日进度同步

#### 备选方案

1. **单一 Agent 全栈开发**
   - 优点：沟通成本低
   - 缺点：专业深度不足，易出错

2. **两阶段开发（先逆向后开发）**
   - 优点：阶段清晰
   - 缺点：周期长，反馈慢

#### 理由

- 专业化分工提升质量
- 并行工作缩短周期
- 文档驱动降低沟通成本
- 明确责任便于追踪

#### 影响

- 需要建立协作机制
- 文档工作量增加
- 依赖管理复杂度提升

### DEC-002: 技术栈选择

**日期**: 2026-03-15  
**提出者**: PM-Agent  
**状态**: ? 已确认

#### 后端技术栈

- **语言**: Go 1.22+
  - 理由：性能优异，并发友好，部署简单

- **Web 框架**: Gin
  - 理由：生态成熟，性能好，API 友好

- **SSE 处理**: 手动实现
  - 理由：依赖少，可控性强

#### 前端技术栈

- **框架**: React 18 + TypeScript
  - 理由：类型安全，生态丰富

- **样式**: Tailwind CSS
  - 理由：开发效率高，响应式友好

- **打包**: Vite
  - 理由：开发体验好，构建快速

- **桌面**: Electron
  - 理由：跨平台，成熟稳定

#### 备选方案

1. **后端：Rust**
   - 优点：性能更好
   - 缺点：学习曲线陡峭，开发效率低

2. **前端：Vue/Svelte**
   - 优点：语法简洁
   - 缺点：生态不如 React

#### 理由

- 平衡性能和开发效率
- 团队熟悉度高
- 生态成熟，问题易解决

**状态**: ? 已实施

1. 先写文档，后写代码
2. 文档与代码同步更新

- 多 Agent 协作需要清晰接口定义
- 减少返工和误解
- 便于知识传承
- 提升代码质量

### DEC-006: 账号存储加密方案

**提出日期**: 2026-03-15  
**提出者**: Auth-Agent  
**状态**: ? 待讨论

#### 背景

账号池需要加密存储用户账号信息，需要选择加密方案。

#### 选项

1. **AES-256-GCM**
   - 优点：安全性高，性能好
   - 缺点：需要密钥管理

2. **ChaCha20-Poly1305**
   - 优点：软件实现性能更好
   - 缺点：相对较新

3. **使用系统密钥链**
   - 优点：安全性最高
   - 缺点：跨平台复杂

#### 建议

使用 AES-256-GCM，理由：
- 成熟稳定
- Go 标准库支持
- 性能优异

#### 决策者

PM-Agent + Auth-Agent

### DEC-007: 队列调度算法选择

**提出日期**: 2026-03-15  
**提出者**: Queue-Agent  
**状态**: ? 待讨论

#### 背景

请求队列需要选择合适的调度算法。

#### 选项

1. **多级反馈队列 (MLFQ)**
   - 优点：公平性好，响应快
   - 缺点：实现复杂

2. **简单优先级队列**
   - 优点：实现简单
   - 缺点：可能饿死低优先级

3. **轮询 + 权重**
   - 优点：公平
   - 缺点：实现复杂

#### 建议

使用简单优先级队列，理由：
- 实现简单
- 满足初期需求
- 后期可升级

PM-Agent + Queue-Agent
